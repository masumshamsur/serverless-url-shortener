### Concepts introduced

**What gets committed vs. ignored in a Terraform project, and the one
exception.**

- `terraform.tfstate`(`.backup`): never committed — can contain sensitive
  attribute values, and committing it would immediately conflict between
  any two people's (or CI's) local runs.
- `.terraform/`: never committed — downloaded provider binaries,
  regenerated by `terraform init`; committing it bloats the repo with
  per-platform binaries for no benefit.
- `.terraform.lock.hcl`: **is** committed — the deliberate exception. Small
  and human-readable, it pins the exact provider version/checksums so
  `terraform init` in CI resolves to the identical provider version used
  locally (see Phase 1, Step 1's provider-pinning concept). This is exactly
  why it matters for Phase 3: without it, CI's `terraform validate` could
  silently run against a different provider version than what was tested
  locally.
- `terraform/build/*.zip`: never committed — generated by `terraform apply`
  from source via `archive_file`; a committed copy would go stale the
  moment `app.py` changes.

## Step 2 — OIDC identity provider + trust policy

**What was built:** `terraform/github-actions.tf` — a data-source reference
to the account's existing GitHub Actions OIDC provider (created previously
by another project; IAM allows only one per URL per account, so we look it
up rather than create a duplicate), and a new IAM role
(`url-shortener-github-actions-deploy`) whose trust policy only allows
`sts:AssumeRoleWithWebIdentity` from that provider, gated by two
`StringEquals` conditions on the token's claims. No permissions policy yet
— the role can be assumed but can't do anything (that's Step 3).

```hcl
data "aws_iam_openid_connect_provider" "github_actions" {
  url = "https://token.actions.githubusercontent.com"
}

data "aws_iam_policy_document" "github_actions_assume_role" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [data.aws_iam_openid_connect_provider.github_actions.arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:masumshamsur/serverless-url-shortener:ref:refs/heads/main"]
    }
  }
}

resource "aws_iam_role" "github_actions_deploy" {
  name               = "${var.project_name}-github-actions-deploy"
  assume_role_policy = data.aws_iam_policy_document.github_actions_assume_role.json
}
```

**Side fix made in this step:** `terraform plan` surfaced an unplanned
`create_link` update (`source_code_hash` changing with no `app.py` edit).
Root cause: `archive_file` zips the literal filesystem contents of
`source_dir`, ignoring `.gitignore` entirely — an earlier local
`python3 -c` test had regenerated `src/create_link/__pycache__/`, which got
zipped into the deployed package. Fixed by adding
`excludes = ["__pycache__"]` to both `archive_file` blocks in `lambda.tf`,
permanently preventing local test artifacts from ever being packaged again.

**Commands run:**
```bash
terraform plan     # 1 to add (role), 1 to change (create_link repackage)
terraform apply
aws iam get-role --role-name url-shortener-github-actions-deploy \
  --query "Role.AssumeRolePolicyDocument"
curl -s -X POST https://<endpoint>/links -H "Content-Type: application/json" \
  -d '{"url": "https://example.com"}'    # regression check after repackage
```

**Result:** trust policy verified against live AWS — both `aud` and `sub`
conditions present, `sub` exactly matching
`repo:masumshamsur/serverless-url-shortener:ref:refs/heads/main`.
Regression check confirmed `create_link` still works after the repackage
(`201` with a fresh short code).

**Status:** ✅ complete.

### Concepts introduced

**What OIDC federation replaces.**
The old pattern: a long-lived AWS access key + secret pasted into a GitHub
secret — works forever until manually revoked, from anywhere, not just CI.
OIDC federation replaces this with short-lived, per-run credentials: for
each workflow run, GitHub's runner presents a freshly-signed identity token
to AWS STS, which verifies it against a role's trust policy and issues
temporary credentials (default 1 hour) scoped to that one role — never
stored as a static secret.

**The OIDC identity provider (IdP) is a one-per-account resource.**
`aws_iam_openid_connect_provider` (or here, the corresponding data source)
registers that AWS IAM should trust tokens signed by
`token.actions.githubusercontent.com`, validated via a certificate
thumbprint. IAM permits only one per unique URL per account — reuse an
existing one via a data-source lookup rather than trying to create a
second, which would error. This is a lookup, not an "import": the
resource isn't brought into this project's Terraform state or ownership.

**The trust policy `Condition` block is what actually enforces scope — not
the IdP's mere existence.**
Registering the IdP just tells AWS "tokens signed by GitHub are
cryptographically valid" — it says nothing about *whose* GitHub tokens a
given role should accept. That scoping lives in each role's trust policy,
matching the token's `sub` (subject) claim, e.g.
`repo:masumshamsur/serverless-url-shortener:ref:refs/heads/main`. Get this
wrong (too broad, or a careless `StringLike` wildcard) and any GitHub
Actions workflow whose token satisfies the pattern — including from repos
never intended — can assume the role.

**The `aud` (audience) claim, alongside `sub`.**
A separate claim from `sub`, asserting the token was minted specifically
*for* AWS STS as the intended recipient (GitHub's official
`aws-actions/configure-aws-credentials` action sets this automatically).
Checking both is the recommended pattern: `aud` confirms "this token was
meant for AWS," `sub` confirms "and specifically for this repo+branch."

**`archive_file` zips the filesystem, not the git index.**
`.gitignore` has no bearing on what `archive_file` includes — it operates
on `source_dir`'s literal contents at apply time. Build artifacts or caches
regenerated locally (like `__pycache__`) can silently end up in a deployed
Lambda package and cause misleading diffs on the next `plan`, unless
explicitly excluded via the `excludes` argument.

## Step 3 — Permissions policy: `UpdateFunctionCode` only

**What was built:** an inline policy on `github_actions_deploy`, granting
exactly `lambda:UpdateFunctionCode` on exactly the two project function
ARNs — no `InvokeFunction`, no config changes, no wildcard resource, no
access to any other AWS service.

```hcl
data "aws_iam_policy_document" "github_actions_deploy" {
  statement {
    effect  = "Allow"
    actions = ["lambda:UpdateFunctionCode"]
    resources = [
      aws_lambda_function.create_link.arn,
      aws_lambda_function.redirect.arn,
    ]
  }
}

resource "aws_iam_role_policy" "github_actions_deploy" {
  name   = "${var.project_name}-github-actions-deploy"
  role   = aws_iam_role.github_actions_deploy.id
  policy = data.aws_iam_policy_document.github_actions_deploy.json
}
```

**Commands run:**
```bash
terraform plan     # 1 to add
terraform apply
aws iam get-role-policy --role-name url-shortener-github-actions-deploy \
  --policy-name url-shortener-github-actions-deploy --query "PolicyDocument"
```

**Result:** verified against live AWS — exactly one action
(`lambda:UpdateFunctionCode`), exactly two resource ARNs (the project's two
functions), no wildcard.

**Status:** ✅ complete.

### Concepts introduced

**Scoping CI's permissions to the single verb it actually needs.**
The Lambda API has dozens of actions (`CreateFunction`, `DeleteFunction`,
`UpdateFunctionConfiguration`, `InvokeFunction`, `AddPermission`, etc.).
This pipeline's only job is "push new code to an existing function" — it
should never be able to invoke the functions, change their IAM role or
environment variables, or delete them. `lambda:UpdateFunctionCode` is the
one action for exactly that, and scoping `Resource` to the two literal
function ARNs (never `*`) means even a fully compromised CI run can only
ever push code to these two functions — not the DynamoDB table, API
Gateway, IAM, or any unrelated Lambda function in the account. Same
least-privilege principle as the Lambda execution role in Phase 1 Step 3,
applied to a different actor (CI) with an even narrower single verb.

## Step 4 — `deploy.yml`

**What was built:** `.github/workflows/deploy.yml` — two jobs. `validate`
runs on every push/PR to `main`, needs no AWS credentials
(`terraform init -backend=false`, `terraform validate`,
`terraform fmt -check -recursive`). `deploy` runs only on an actual push
to `main` (`if: github.ref == 'refs/heads/main' && github.event_name ==
'push'`), `needs: validate`, assumes the OIDC role via
`aws-actions/configure-aws-credentials@v4`, then zips and
`aws lambda update-function-code`s both functions directly (no Terraform
in this job — see the "why hardcoded names" note below).

```yaml
jobs:
  validate:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: "1.16.3"
      - run: terraform init -backend=false
      - run: terraform validate
      - run: terraform fmt -check -recursive

  deploy:
    needs: validate
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      id-token: write
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::842190336606:role/url-shortener-github-actions-deploy
          aws-region: us-east-1
      - run: |
          cd src/create_link && zip -r ../../create_link.zip .
          aws lambda update-function-code --function-name url-shortener-create-link \
            --zip-file fileb://../../create_link.zip
      - run: |
          cd src/redirect && zip -r ../../redirect.zip .
          aws lambda update-function-code --function-name url-shortener-redirect \
            --zip-file fileb://../../redirect.zip
```

**This step included a real debugging saga** — the OIDC trust policy
initially failed with `Not authorized to perform
sts:AssumeRoleWithWebIdentity` on every attempt. Full diagnosis (a
temporary JWT-decoding debug step, root cause, fix) is written up in
[`troubleshooting.md`](./troubleshooting.md) entry #1 rather than
duplicated here — short version: GitHub's real `sub` claim is
**ID-qualified** (`repo:owner@ownerId/repo@repoId:ref:...`), not the
plain-name format the trust policy was originally written with. Fixed by
updating the `sub` condition value to match the real, decoded token, then
removed the temporary debug step once confirmed working.

**Commands run (final, working sequence):**
```bash

terraform apply
cd ..
git add terraform/github-actions.tf
git commit -m "Fix OIDC trust policy: use GitHub's ID-qualified sub claim format"
git push
gh run list --limit 2
```

**Result:** run `36368491904` — both jobs green. `Configure AWS

**Status:** ✅ complete.

### Concepts introduced

**Job-level `permissions` for OIDC.**
A job's default token has no `id-token` permission — it must be declared
explicitly:
```yaml
permissions:
  id-token: write
  contents: read
```
`id-token: write` is what lets the job request an OIDC token from GitHub
at all; without it, `configure-aws-credentials` fails before ever reaching
AWS. This is a deliberate opt-in security control on GitHub's side too —
no third-party Action in the workflow can silently start requesting AWS
credentials unless the job explicitly grants this.

**`aws-actions/configure-aws-credentials` performs the actual OIDC
handshake.**
Requests a token from GitHub (audience `sts.amazonaws.com`), calls
`sts:AssumeRoleWithWebIdentity` against `role-to-assume`, and exports the
resulting temporary credentials as environment variables for every
subsequent step in the job. The credentials are never seen or handled
directly in workflow code.

**Two jobs, one trigger, different conditions.**
Both jobs run on push/PR to `main`, but `deploy` adds
`if: github.ref == 'refs/heads/main' && github.event_name == 'push'` and
`needs: validate`. A PR against `main` runs `validate` only (catching
Terraform errors pre-merge) and never attempts a deploy; only an actual
push to `main` triggers `deploy`, and only after `validate` passes.

**`terraform validate` still needs `terraform init`, just not credentials.**
`init` sets up the working directory (downloads providers) even though
`validate` itself makes no AWS calls. `terraform init -backend=false`
skips backend initialization, keeping the whole `validate` job genuinely
credential-free — also what you'd need with a remote backend to avoid
requiring credentials just to check syntax.

**GitHub's ID-qualified OIDC `sub` claim.**
The real `sub` claim format is `repo:owner@ownerId/repo@repoId:ref:...`,
not just `repo:owner/repo:ref:...`. This is actually more robust than the
plain-name form — the numeric IDs survive a repo or username rename, while
a plain-name trust policy would silently stop matching after either. See
[`troubleshooting.md`](./troubleshooting.md) for the full diagnosis.

**Debugging a federated-identity failure by decoding the real token.**
`Not authorized` (a trust-policy condition mismatch) is a different
failure mode from an `Invalid identity token` error (an IdP
registration/thumbprint problem) — the error text itself narrows where to
look. For the former, don't guess the claim format from memory or docs:
request the actual token and decode its JWT payload (just base64, not
encrypted) to see the real values. This generalizes well beyond
AWS+GitHub to any OIDC/JWT-based debugging.
